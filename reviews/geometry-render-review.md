# Independent geometry/render review

Reviewed `renderer/scene.py`, `renderer/worker.py`, their CPU tests, the proof controller, and the Rust mesh/bead contract against the first-foundation scope in `final-plan.md`. No renderer or root-owned source was changed. Review performed after the Rust core's 18 tests and integrated CLI tests passed.

## Important findings

### 1. Smooth bead caps contaminate the side normals

`renderer/scene.py:165–167` marks every bead polygon smooth. The Rust bead generator shares each endpoint ring between side faces and its cap fan. Blender includes the smooth cap in the endpoint corner-normal calculation, tilting the visible bead wall toward the path direction. Because this prototype represents each motion segment independently, the incorrect axial component repeats at every endpoint, rather than only at the beginning/end of a continuous printed path. This can produce apparent seams and highlight variations unrelated to the chosen layer height or actual bead profile.

This was confirmed with an actual CPU mesh probe in the installed Blender **4.5.2 LTS, build ab25eae04993**. A straight extruded four-point ring with the same side/cap sharing emitted:

```text
ALL_SMOOTH_SIDE_CORNER (-0.5773675441741943, 0.8164843916893005, 0.000009683006283)
FLAT_CAP_SIDE_CORNER  (0.0, 1.0, 0.000011859388906)
```

The expected side normal has no axial X component. Marking cap polygons flat removes the cap contribution in this Blender build. Required fix: preserve smooth bead side walls but give caps separate/flat shading. Identify caps through a deliberate, verified geometry contract; the generic meshbin v1 itself has no face-kind attribute. Options include explicit layout metadata in the scene for this known bead producer, separate normals/face attributes in a new mesh version, or a topology-based cap classifier. An undocumented global `triangle_index % 4` assumption would couple the renderer to an incidental producer ordering.

Acceptance: a live Blender regression asserting zero axial component for a straight bead's side corner normal; a cap normal aligned with the path; and inspection of the final rotating fixture after the correction. The existing overlapping capped-join approximation can remain documented; smoothing its caps is a separate avoidable error.

### 2. Reader validation now disagrees across the shared format

`renderer/scene.py:12` defaults to **5,000,000 vertices / 10,000,000 triangles**, while Rust's `src/mesh.rs:8–9` permits **2,000,000 / 4,000,000**. The Python reader also accepts degenerate triangles; Rust's snapshot reader/writer now reject triangles that have zero area after f32 conversion. The Rust precision regression exposed a real case where finite coordinates around a large offset collapse a bead's thin cross-section in the serialized format.

A pure-Python probe confirmed that Python accepts the collinear triangle `(0,0,0), (1,0,0), (2,0,0)` with indices `(0,1,2)`, which Rust rejects. This discrepancy weakens the promise that both sides validate the same mesh and permits significantly larger allocations in the Python/Blender path than the application budget.

Required fix: align the default limits and reject degenerate faces in Python before constructing Blender geometry. Test count rejection before payload allocation and a complete collinear/duplicate-index fixture. Format documentation should state the same budget/degeneracy policy on both sides. A normal small fixture generated by Rust is unaffected, so the live rendering experiment can continue while this is corrected.

## Findings that can remain documented in this foundation

- **There is no scene/mesh cache yet.** `worker.render()` calls `build_scene()` on each request; it reloads the mesh, removes the previous geometry/material/light/camera datablocks, and reconstructs the studio. This avoids stale cached geometry. Two requests in one process prove persistence, but do not prove warm mesh reuse. Record preparation time and describe this accurately; cache optimization is not required to finish the current proof.
- **Hash reflects a second file read.** `build_scene()` reads the mesh for geometry and hashes the path again afterward. If the file changes between those reads, the reported hash could describe different bytes. Job files are intended to be immutable, so this is a low-risk foundation limit. A future cache/reuse implementation should hash the bytes actually consumed or verify immutability before associating the hash with rendered geometry.
- **Maximum-size interfaces differ.** The proof controller permits sizes through 8192, while the worker permits through 8000 (the latter respects the plan's 64 MP square limit). An oversized request produces a useful worker error rather than corrupt output. Align help/validation before presenting custom dimensions as a polished user feature.
- **Mesh ingest duplicates Python data.** The reader materializes tuples, then rotated tuples, then centered tuples, then Blender mesh data through `from_pydata`. The current 1.6-million-triangle fixture measures that real path; it is not evidence that the declared maximum is inexpensive. Report system memory and preparation time separately from GPU render time. Bounded array ingestion can follow the proof.

## Geometry/camera checks that look correct

- Rust already places bead centers at `nozzle_z - height/2`; the renderer applies exactly `0.001` meters per millimeter. There is no second half-layer shift. Display rotation is baked into these physical vertices before floor placement.
- Centering displayed XY and translating the displayed minimum Z to the floor preserves bead dimensions and spacing. The turntable then rotates about studio Z at the centered origin. This is appropriate for presentation rotation independent of the nominal build direction.
- The radius is the maximum XY distance from the displayed bounds center, and height is the displayed Z extent. The sphere of radius `hypot(radius,height/2)` therefore contains the complete swept cylinder. With square pixels/output and the chosen horizontal sensor fit, `sphere_radius / sin(half_fov) * 1.10` is a conservative perspective fit for every spin angle. The near/far clipping distances also encompass that sphere.
- The worker chooses a fixed object mesh, camera, lights, exposure and engine for the sequence. Angles omit the duplicated endpoint. It does not switch geometry detail as the camera rotates.
- Unsupported engine/mode and malformed scene inputs are checked; errors are returned with request identity, and the main command loop continues. Existing output paths are refused before rendering. Frames use temporary names, decode/dimension checks, then publication.

The camera unit test currently checks only an envelope's radius/height, not projection through all angles. The algebra above supports correctness for the current square-only interface; add projected-corner coverage when rectangular outputs or custom cameras arrive.

- Pure-Python malformed-mesh probe reproduced acceptance of collinear geometry.
