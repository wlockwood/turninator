# LuxCore desktop integration

LuxCore is an optional, in-process Windows x64 CUDA/OptiX path tracer. Select it independently for animations and still images in the desktop renderer controls. Native wgpu and Filament remain the interactive viewport choices. No Blender or renderer helper process is required for LuxCore preview, PNG or four-view sheets. GIF requires FFmpeg; MP4 also requires ffprobe.

The full package supplies `renderers/luxcore/tn_renderer_luxcore.dll`, its `luxcore-package.json` receipt and ten pinned runtime files. The host validates every file before loading and verifies the actual loaded SDK, compiler, denoiser, OpenMP and CUDA/OptiX driver artifacts. Missing files, mismatched hashes, an unavailable selected device or an unsupported machine produce an error for LuxCore. The application retains the selected renderer and never substitutes another one. Current qualification covers Windows x64 with AVX, NVIDIA CUDA/OptiX and the recorded RTX 4070 Ti driver; it does not establish support for other hardware.

Transparent resin images and sheets use approximate RGBA compositing. Use an opaque studio still for consistent refraction. Denoised fine-layer animation is also approximate: disable denoising for stable fine-layer detail. The UI and export report expose these warnings without changing material or renderer choices. Opaque volume absorption/scattering and raw physical layer shading have separate qualification.

Samples mean a minimum per output pixel, with effective AA and actual sample counts recorded in native diagnostics. Request64 uses AA9 and measured80..82 samples. OIDN2.5 CPU RT High prefilters albedo/normal guides before beauty filtering. Camera alpha is preserved independently; linear radiance is unpremultiplied before shared AgX conversion. A positive deterministic seed derives from the complete immutable pixel recipe, including the resolved frame plan, and stays fixed across that job's poses. Each pose resets accumulation.

`LuxCoreBackend::new(&EmbeddedConfig)` owns a standalone lifetime. The application constructs a `LuxCoreRuntimeCache` inside its export actor and calls `prepare` across jobs, retaining one idle, scene-free native owner until actor shutdown. Backends and the cache cannot cross threads. Explicit lexical destruction joins the native SDK owner before DLL unload; SDK objects are never stored in Rust thread-local destructors. Job contexts release their GPU resources on switching. Replacing an installed runtime requires restarting the application. The Filament viewport waits for an export-context release acknowledgement before resuming.

The compiler cache lives in `.luxcore-kernels` under the application's job-cache directory and is separate from retained frame artifacts. No environment variables, PATH search, downloads or global cache deletion are used. Runtime discovery is descriptive and does not load the SDK. Preparation validates the package/device and reserves memory before expensive work. Kernel compilation is measured separately and may delay cancellation; a hung graphics driver cannot be made recoverable solely by an API timeout.

The default8 GiB host allowance is insufficient for the conservative reservation of a4096-square OIDN job. Increase the host maximum to16 GiB in Tools / storage before rendering; this is an allocation ceiling, not a claim about installed/free RAM or VRAM. See [native implementation and measurements](luxcore-native.md) and [package qualification](qualification-matrix.md) for evidence and limits.
